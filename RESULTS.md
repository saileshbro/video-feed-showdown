# DartNative vs Flutter — infinite video feed: results

Everything in this file is measured from a captured `##BENCH##` event
stream (`lib/bench.dart`, byte-identical in both apps) parsed by
`bench/parse_bench.py`. An earlier draft of this comparison contained
invented benchmark numbers, written before Flutter was ever compiled on
this machine — none of that carries forward. Every figure below traces
to a raw log in `bench/*.log`.

## Setup

- **Apps**: `dartnative/` and `flutter/` in this repo,
  built from the same `lib/feed_config.dart` (byte-identical, generated by
  `bench/gen_items.py`) — 13 verified-alive Pexels MP4s, `FEED_COUNT=1000`,
  same pool window (1 behind + focused + 2 ahead), same 3-controller cap,
  same 250ms dispose grace, same `BoxFit.cover` crop.
- **Devices**: iPhone 16 Pro Max running iOS 26.6.1 (physical, cabled,
  `dn run --profile` / `flutter run --profile`), and iPhone 17 Pro Max
  simulator, iOS 26.4 (`dn run` / `flutter run`, debug — see caveats).
- **Interaction**: momentum-free `gesture-swipe` via argent
  (`durationMs: 600, momentum: false`), so each swipe is a deterministic
  drag rather than a simulated fling of unknown speed.

## Known asymmetry: caching

DartNative's `dartnative_video_player` has built-in byte-range pre-cache
(`VideoCache.preCache`) and a 100MB disk cache; `video_player` has
neither. Both apps run the same network-source Pexels URLs, so **TTFF
below reflects this ecosystem gap, not a framework-level decode
difference.** A `SRC=local` code path exists in both apps (bundled
assets, no network) to isolate the render pipeline from caching, but
those local assets were not bundled for this run — flagged as follow-up.

## 1. Paging: DartNative ships none

Verified against DartNative's own sources (`~/Projects/dartnative`,
matching the installed `3.45.0-0.1.pre` SDK):

- `docs/widgets.md`: `PageView` — ❌ **Not planned**.
- `skills/dart-native/SKILL.md`: *"`PageView` (not planned) → Restructure:
  `SegmentedControl`/tabs + `IndexedStack`, or a horizontal `FastList`"* —
  no guidance for a vertical full-screen paged feed.
- The playground's own `carousel_demo.dart` header: *"Built by hand
  instead of with a scroll view: there is no paging API."*
- `FastListController` (`fast_list.dart`) is index-only —
  `jumpToItem`/`scrollToItem`/`animateToItem`. For a row exactly one
  viewport tall, every `alignment` value resolves to the same offset, so
  a finger-following pager cannot be built on it from Dart at all.

**What works**: `UIScrollView.pagingEnabled`, set from Dart via a 22-line
Objective-C shim (`ios/Runner/DNPaging.m`) exposed as a C symbol and
called through `DynamicLibrary.process()`. Verified:

- Paging engages ~2ms after first frame (`paging_native: {"code":1}` in
  the bench log — no delegate override, `decelerationRate: 0.998`).
- **A safe-area inset breaks alignment.** `pagingEnabled` steps by exactly
  `bounds.height`; any inset leaves every page short by that amount — a
  visible sliver of the previous video stays on screen. Full-bleed feed:
  `contentInsetAdjustmentBehavior = .never` and `contentInset = .zero`
  fixes it.
- **`contentSize` has a breaking point.** Paging snaps correctly at 40 and
  at 1000 rows (`content=440x956000`, offsets land on exact multiples of
  956) but silently stops snapping at 10000 rows
  (`content=440x9560000` — the list just rests wherever the finger left
  it). `kFeedItemCount` in both apps is pinned to 1000 for this reason —
  see the comment in `feed_config.dart`.
- Deferring the settle callback off the native scroll thread
  (`Future.microtask`) is required — calling `setState` synchronously
  from inside `FastList`'s native scroll callback wedges the scroll view
  (observed directly: a fling stopped responding to touch entirely until
  the callback was deferred).

**Result: yes, PageView-equivalent interaction is achievable — with a
native plugin, an inset gotcha, and a content-size ceiling that would
easily bite someone building a truly unbounded feed.**

## 2. Interaction-feel difference (not a bug)

Five identical scripted swipes (same coordinates, same 600ms duration,
`momentum: false`) landed differently on each app:

| App | Landed on |
|---|---|
| DartNative (native `pagingEnabled`) | `#5` — one page per swipe |
| Flutter `PageView` | `#14` — some swipes advanced multiple pages |

Both are "real" native-feeling paging; `PageView`'s ballistic scroll
physics simply translate the same synthetic gesture into more distance
per swipe than `UIScrollView.pagingEnabled` did here. This is a
qualitative flavor difference to call out in the post, not a defect in
either implementation.

## 3. Startup & TTFF

`startup_ms` = `main_enter` → `first_frame`. `ttff_ms` = per-row
`ctrl_create` → `ctrl_ready` (player constructed → first frame decodable),
median/min/max across every row created during the session.

### Physical device (iPhone 16 Pro Max, iOS 26.6.1, `--profile`)

| | DartNative | Flutter |
|---|---|---|
| Startup (main → first frame) | **863ms** | *(not obtained — see below)* |
| TTFF median (n=48) | **88ms** | — |
| TTFF min / max | 52ms / 2388ms | — |
| Settle → play median (n=41) | 1ms | — |
| Errors | 0 | — |

**Flutter would not launch on the physical device in profile mode.**
Four separate `flutter run --profile -d <device>` attempts each hung at
"Installing and launching" for 8–10 minutes with no VM Service ever
discovered, no crash report (`idevicecrashreport` — clean), and the app
process confirmed alive on-device via `devicectl device info processes`.
A direct `devicectl device process launch` succeeded in one case, but
`flutter attach` still could not find a VM Service on the resulting
process. DartNative's own `dn run --profile` needed one retry the first
time (same device) then ran reliably on every subsequent launch — so
this reads as a Flutter/CoreDevice tooling problem on this specific
iOS 26.6.1 device, not a device-connectivity problem generally. Flagged
as a real finding for the blog post (`flutter run` device attach
reliability), not swept under the rug.

### Simulator (iPhone 17 Pro Max, iOS 26.4, debug — apps run one at a
time, fully terminated between runs to avoid `os_log` cross-talk)

| | DartNative | Flutter |
|---|---|---|
| Startup (main → first frame) | 1371ms | 548ms |
| TTFF median | 293ms (n=7) | 1091ms (n=28) |
| TTFF min / max | 33ms / 2188ms | 262ms / 2541ms |
| Settle → play median | 30ms (n=5) | 0.4ms (n=26) |
| Errors | 0 | 0 |

**Debug-build simulator numbers are not representative of real
performance** — no JIT/AOT parity between the two, no hardware decoder
path, and DartNative's smaller TTFF-n here is simply "fewer rows were
swiped through before the log was cut," not a stronger result. They are
included only as directional, same-device, same-session evidence,
clearly separated from the physical-device numbers above.

## 4. What wasn't measured, and why

- **Memory (RSS) and jank/frame-drop counts**: not captured this pass.
  `xctrace list devices` does see the physical iPhone
  (`SAILESHBRO (26.6.1)`), so `xctrace record` against both apps is the
  next step — blocked here by the Flutter device-launch issue above.
- **Binary size**: DartNative profile build measured at **26.1MB**
  (`dn build ios --profile --no-codesign`, 29.9s build). No equivalent
  Flutter release build was produced this pass.
- **`SRC=local` TTFF** (network-free, isolates the render pipeline from
  Pexels/caching): code path exists in both apps but the curated 13-file
  media set (`bench/media/`, 124MB, downloaded and verified 200 OK) was
  never bundled as app assets, so this number doesn't exist yet.

## Repro

Screen recordings of both apps on the same simulator session, same
interaction: `bench/repro/`. Two pairs of clips —

- `*-scroll-autoplay.mp4`: 4 flicks + 1 back, showing one-flick-one-page
  paging and autoplay tracking the settled page in both apps.
- `*-fast-scroll-loadtest.mp4`: 8 rapid swipes (500ms apart), deliberately
  faster than the 2-ahead preload window. DartNative's paging is locked
  to one page per swipe, so every landed row was already warm — no
  visible stall across 8 swipes (TTFF median **62ms**, n=10, see below).
  Flutter's `PageView` carries further per swipe on the same gesture and
  lands on rows the pool never preloaded — a buffering spinner is visible
  mid-clip (TTFF median **1207ms**, n=33). One row hit a real network
  timeout under the stress (`PlatformException(VideoError, ... The
  request timed out ...)`) — zero errors across every DartNative run in
  this file.

This is the direct evidence behind "DartNative loads noticeably faster":
same device, same session, same swipe script, and the gap is visible on
screen, not just in the log.
